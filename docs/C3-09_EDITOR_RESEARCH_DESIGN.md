## Предлагаемый дизайн (только проект, без кода)

```text
[C3-04 admission: уже принятый материал]
               |
               v
[Input envelope: material_type, text, source IDs, canonical URLs,
 event IDs, publication/observation dates, source excerpts]
               |
               v
[Deterministic gate: обязательные поля, URL, числа/единицы,
 даты, дедупликация, привязка цитат и provenance]
               |
               v
[Atomic claim extraction: бесплатная модель + строгая JSON-схема]
               |
               v
[Evidence alignment: для каждого claim первоисточник/фрагмент,
 contradiction / supported / insufficient / unavailable]
               |
               v
[Reasoning gate: причинность, масштаб вывода, временной порядок,
 чужой контекст, разделение факта/оценки/прогноза]
               |
               v
[Decision: PASS | REVIEW | BLOCK; список причин + evidence IDs]
               |
               +--> PASS: только разрешение следующему этапу публикации
               +--> REVIEW/BLOCK: удержать, передать человеку/на исправление
```

**Выпускающий редактор не публикует самостоятельно и не меняет записи.** Он возвращает вердикт и audit trail; фактический publisher отдельно проверяет вердикт и полномочия. При ошибке API, таймауте, отсутствующем первоисточнике или невалидном JSON: fail closed (REVIEW/BLOCK, не PASS). Для сигналов и аналитики отдельно проверять ссылки на синтезы и базовые факты; чужие аналитические мнения не считать первичными доказательствами. Не смешивать источник, его пересказ и вывод.

### Обязательный контракт проверки

Вход: `material_id` (для синтезов также `synthesis_id`), `version`, `content_hash`, `evidence_set_hash`, `material_type` (`synthesis|signal|analysis`), `text`, `event_ids`, `sources[]` с `source_id`, `url`, `published_at`, `retrieved_at`, `excerpt`, `provenance`; `context_items[]` с привязкой к событиям. Отсутствие обязательного поля — REVIEW/BLOCK, не выдумывать значения. Для публикации строго требуется совпадение всех идентификаторов версии и хешей, как определено ниже.

Выход: `decision`, `material_id`, `synthesis_id` (если применимо), `version`, `content_hash`, `evidence_set_hash`, `reasons[]` (`rule_id`, `severity`, `claim_id`, `source_ids`, `explanation`), `claims[]` (`claim_text`, `evidence_span_ids`, `verdict`), `checker_versions`, `model_id`, `checked_at`. Не выводить секреты, скрытые prompt или приватный текст в публичный лог.

### Список проверок (предложение)

| ID | Проверка | Механизм | Если не прошла |
|---|---|---|---|
| E01 | Реальная ссылка, корректный URL и источник в allowlisted evidence | Код + сохранённые provenance | BLOCK при поддельной ссылке; REVIEW при недоступности |
| E02 | Числа, валюта, единицы, проценты, диапазоны и цитаты соответствуют первоисточнику | Извлечение + буквальная/нормализованная сверка | BLOCK при расхождении |
| E03 | Каждое существенное атомарное утверждение имеет релевантный фрагмент | FActScore-подобная декомпозиция + entailment | REVIEW при недостатке, BLOCK при противоречии |
| E04 | Контекст принадлежит тому же событию, компании, программе и периоду | ID/entity/time matching + LLM adjudication | BLOCK при чужом контексте |
| E05 | Вывод не сильнее доказательств; гипотеза маркирована как гипотеза | LLM rubric с цитируемыми spans | REVIEW/BLOCK |
| E06 | Нет дубля того же события (не путать с несколькими независимыми источниками) | совпадение событий между опубликованными материалами, сущностями, датами и источниками; canonical event ID только как один сигнал | REVIEW/BLOCK |
| E07 | Даты публикации, события и прогнозов упорядочены | Детерминированная проверка + temporal LLM | BLOCK при противоречии |
| E08 | Противоречащие источники и неопределённость не скрыты | Сопоставление claims и evidence | REVIEW |
| E09 | Факт, мнение аналитика и прогноз разделены | Типизация claims | REVIEW |
| E10 | Не исполняются инструкции, найденные внутри новостей/страниц | Treat source as untrusted data; delimiter/schema | BLOCK при признаках компрометации |
| E11 | Не теряются обязательные оговорки и география | Сравнение с первоисточником | REVIEW |
| E12 | При сбое модели, исчерпании бесплатного лимита или ошибке JSON публикация запрещена | Fail-closed код | BLOCK/REVIEW |

**Правило:** high-severity E01–E04/E07 -> BLOCK; недостаточность evidence -> REVIEW; PASS только если все обязательные проверки завершились. Один общий score не может перекрыть критическую ошибку. Приоритет проверок: сначала дешёвый детерминированный слой, затем минимальные бесплатные вызовы Groq/Gemini, только по спорным claims; никакого платного fallback без отдельного решения владельца.

Это нормативная **проектная спецификация для будущей C3-10**, а не описание готовой реализации. Основание: [комментарий владельца с проверкой Claude](https://github.com/nab0k/bohun-the-field/pull/176#issuecomment-6639873159). Свидетельства о локальных экспериментах ниже приведены **со слов ревью**, без доступа к локальным данным и без самостоятельной проверки.

### 1. Вердикт привязан к точному опубликованному представлению

- `PASS` связывается с неизменяемым кортежем `(material_id, synthesis_id?, version, content_hash, evidence_set_hash, editor_policy_version)`. `synthesis_id` обязателен именно для синтеза. Версия обязательна для всех типов.
- `content_hash` вычисляется от канонической сериализации **публикуемого payload целиком**: заголовка, подзаголовка, каждого раздела (включая порядок), цитат, чисел, ссылок и атрибуций источников, географической привязки/точки на карте и остальных полей видимой выдачи. У одинаковых данных одинаковый hash; нормализация и версия сериализации фиксированы. `evidence_set_hash` от отсортированного манифеста source IDs, версий/хешей текстов и spans, provenance и relevant event IDs (не от mutable URL без версии).
- После **любого** автоисправления, ручной правки, удаления секции, перестановки заголовка, изменения ссылок, источников или точки карты предыдущий `PASS` становится недействительным. Новый payload получает `version+1`, пересчитанные хеши и **повторную полную проверку**. Нельзя переносить вердикт на исправленную версию.
- Publisher внутри одной атомарной транзакции/эквивалентной compare-and-swap операции сверяет ID, версию, оба хеша, политику, статус `PASS` и срок действия с сохранённой опубликованной кандидатурой и манифестом доказательств. При несовпадении **не публиковать** и отправить в повторную проверку. Если backend не позволяет атомарную сверку, автоматическая публикация не допускается до решения об эквивалентной защите.
- Тест C3-10: CaseEvak после автоисправления не проходит со старым `PASS`; изменение заголовка, карты, раздела или source URL между проверкой и публикацией блокируется.

### 2. Семантика REVIEW, автоисправление и частичная публикация

`REVIEW` означает **не разрешено к публикации**, но потенциально исправимо без новых доказательств; это не бесконечная ручная очередь владельца. Часы TTL начинаются при первом `REVIEW`, не сбрасываются повторными попытками. Все лимиты ниже **предложения для согласования**, а не внедрённые настройки.

| Тип | Кто решает REVIEW | Автоисправления | TTL от первого REVIEW | После TTL |
|---|---|---|---|---|
| Синтез | Автоматический редактор, только по проверяемым правилам; спорное — в отдельный backlog | не более 2 редакций (включая удаление целой секции) с новой полной проверкой | 24 ч | BLOCK данного варианта, видимая причина; хороший подтверждённый фрагмент можно выпустить только после отдельного PASS новой версии |
| Сигнал | Независимая проверяющая модель плюс правила G2/G5/G6; при нехватке независимых доказательств никто автоматически не одобряет | не более 1 редакции, только формулировки/явные оговорки; нельзя придумывать факты или условие опровержения | 48 ч | BLOCK/архив кандидата с причиной; не публиковать неполный сигнал |
| Аналитика | Ответственный за утверждение владелец, как в C5-03; автоматический редактор только готовит предложения | не более 2 предложений исправления до утверждения | 7 суток | вернуть в неподтверждённые черновики; публичной выдачи нет |

**Частичный исход:** если одна секция содержит чужой контекст и её удаление не ломает подтверждённые выводы, система создаёт **новую версию без секции**, повторно проверяет заголовок, весь оставшийся текст, ссылки, карту и выводы. Публикация допускается только по новому `PASS`. Если без удалённой секции вывод перестаёт подтверждаться, `BLOCK`; не маскировать пустоту. Не делать тихую замену после публикации: новое редактирование снова требует `PASS`. Как сообщает ревью, удаление чужого контекста применялось для 12 материалов C3-08; это кейс для тестирования, а не доказательство работы предложенного редактора.

Очередь хранит код причины, время первой проверки, число попыток, следующую возможность, состояние и отсутствие публичной публикации. Автообработка идёт в пределах бюджета; владелец не обязан разбирать каждый `REVIEW`. Утверждение аналитики владельцем сохраняется.

### 3. Единый канал доказательств с C3-04 / C3-05

Вводится **проектный контракт EvidenceBundle**, а не предположение о готовом `excerpt`. Место хранения: **приватное, ограниченное доступом хранилище исходных документов/фрагментов проекта с манифестом в хранилище метаданных**, конкретная таблица или bucket выбираются при C3-05/C3-10 после просмотра действующей схемы; этот документ ничего в инфраструктуре не создаёт. У записи: `source_id, canonical_url, content_kind(primary|secondary|unknown), publisher, published_at, retrieved_at, extraction_status, text_ref, text_hash, provenance, event_ids, evidence_spans, access_restrictions`.

- C3-04 отвечает за **входной допуск сюжета/новости**, качество источника, структуру контекста и допустимость в рабочем маршруте. C3-05 отвечает за **получение, извлечение и сохранение полного текста либо проверяемого фрагмента с provenance**. C3-10 **только читает тот же EvidenceBundle** и проверяет каждое утверждение *окончательной публикационной версии*; редактор не повторяет логику входного допуска. Контракт один, две стадии с различными задачами.
- Первичный документ (официальный релиз, контракт, отчёт, первичная цитата) предпочтителен. Вторичный материал может подтверждать только то, что он **сообщает**, но не независимо подтверждать первичный факт. Два перепечатавших одно сообщение издания считаются одним корневым источником. При споре или материальном числовом утверждении нужен исходный первоисточник либо `REVIEW`/`BLOCK`.
- Если полный текст не получен, допустим **сохранённый, атрибутированный, проверяемый фрагмент** только для тех claims, которые он буквально поддерживает. При отсутствии проверяемого фрагмента — `insufficient` и REVIEW; при истечении TTL — BLOCK. Не создавать вымышленные spans из title/snippet или результата генерации. Не трактовать непроверенный пересказ как доказательство.
- По замечанию ревью A-11 после правки не подтверждена живым прогоном, C3-05 ещё не завершена; поэтому реальная доля доступного evidence и связанная доля REVIEW пока неизвестны.
- В журналах/PR/публичной трассировке **нет полного текста чужих статей**, секретов или приватных извлечений. Оставлять IDs, хеши, краткие коды ошибок и приватные ссылки на spans с контролем доступа; отдельная политика удержания текста и прав использования до внедрения.

### 4. Пакетная проверка, стоимость и отказоустойчивость

Исходная оценка ревью: Groq **1000 requests/day и 8000 tokens/minute** на общий пул модулей, до **30 синтезов за прогон**. Эти значения не сверены с живой квотой: использовать как **планировочные ограничения**, не обещать как реальные.

**Предложенный фиксированный envelope одного прогона синтезов:** один пакетный вызов **на материал** со всеми atomic claims и компактными evidence spans; не один API запрос на claim. Максимум **30 проверок + 10 повторных проверок изменённых версий = 40 requests/run**, не более **120000 суммарных input+output tokens/run** по планировочному максимуму 3000 tokens/request. При 8000 tokens/minute нижняя граница последовательного расходования токенов ~15 минут, без учёта иных модулей и latency; фактический throughput должен ограничиваться *общим* rate-limit ledger. Если данные не помещаются в 3000 tokens, разбить на проверяемые блоки **только внутри выделенного бюджета** или направить в REVIEW, не скрывать пропущенные утверждения. Оценка 40/1000 = 4% суточной квоты запросов *за один прогон*; 3 прогона — до 120 requests и 360000 tokens (при отсутствии других модулей), поэтому общий диспетчер должен резервировать лимиты между потоками. Это верхняя оценка проектного бюджета, **не результат замера**.

Планировщик перед вызовом рассчитывает остаток общего суточного requests budget, минутного tokens budget, зарезервированную долю других модулей и число ожидающих; ограничение следует брать по фактическим объявленным лимитам аккаунта. При 429/503 допускается один повтор с экспоненциальной задержкой **в том же лимите на прогон**; 3 ошибок 503 на 9 группах, закрытые 60-секундной паузой, упомянуты Claude как результат локальной пробы C4-02, **здесь не воспроизводились**.

**Независимость проверяющего:** модель-редактор должна отличаться от модели-автора минимум по модели; желательно по семейству/provider. Проверка тем же модельным вариантом не считается независимой. Если альтернативной бесплатной модели нет или бюджет исчерпан, детерминированные проверки выполняются, но итог — `REVIEW`, не `PASS`; после TTL — `BLOCK`. **Никакого платного fallback.** Очередь возобновляется при восстановлении квоты, приоритет: изменённые версии с доступными полными доказательствами → старейшие новые синтезы → сигналы/аналитика в рамках собственных квот, с защитой от голодания. Конкретная межмодульная политика согласуется отдельно.

**Наблюдаемость C3-02:** фиксировать `editor_pending, editor_blocked, editor_review_age_hours, editor_quota_exhausted, editor_last_pass_at, editor_stale_feed`. Если свежие материалы не проходят из-за редактора более суток, выдавать **заметную тревогу**, не отмечать пустую/застывшую ленту как успешную поставку. Публикующая система остаётся fail-closed, но сбой не должен быть тихим.

### 5. Дополнительные правила сигналов, стадий и глобальных дублей

| ID | Что проверяется | Условие допуска |
|---|---|---|
| E13 / G2 | База сравнения (baseline) | Явные дата, величина/состояние «до», однородный измеритель и привязка к источнику; без baseline нельзя утверждать изменение |
| E14 / G5 | Независимость первоисточников | Доказательства ведут к независимым корневым источникам; **синтез BOHUN не считается независимым доказательством** |
| E15 / G6 | Условие опровержения | В сигнале сформулировано наблюдаемое событие/порог и срок, после которого гипотеза пересматривается; без фальсификатора сигнал не проходит |
| E16 | Стадия события | `announced → contracted → delivered → demonstrated` отслеживается по типу факта, источнику и дате; нельзя повышать стадию без явного подтверждения (и порядок не является автоматическим жизненным циклом для каждого сюжета) |
| E17 | Заголовок отдельно | В заголовке не должно быть более сильного утверждения, чем в доказанной части текста; отдельно проверить числа, субъект и статус стадии |
| E18 | Глобальные дубли | Сопоставление с **уже опубликованными** материалами по entity/event, датам, первоисточникам и смыслу; canonical ID только вспомогателен |

Примеры из ревью: `syn-364` и `syn-378` названы дублем одного события с разными ID; пара `syn-250`/`syn-300` **предположительно** похожа, требует ручного подтверждения, не объявляется установленным дублем. При совпадении по событию новые факты могут обновить existing story только в отдельной явно разрешённой логике версии; редактор сам не перезаписывает опубликованное. Источник, который цитирует другой источник, **не увеличивает** счётчик независимых доказательств. Для аналитики дополнительно сохранять разделение факта, оценки и прогноза.

### 6. Предлагаемые пороги, статистика и gold set: решение владельца

**Вариант для утверждения, не утверждённый порог:**

| Класс метрики | Предложение первого замера | Знаменатель |
|---|---|---|
| Recall детерминированных ошибок (URL, число, валюта, цитата, дата) | **≥99%** | Все заранее размеченные подложенные ошибки данного класса |
| Recall смысловых ошибок (чужой контекст, противоречие, завышение вывода) | **≥85% как гипотеза**; 95% — цель после shadow run | Все заранее размеченные ошибки данного класса |
| False BLOCK хороших материалов | **≤5%** | Все проверенные человеком качественные материалы |
| REVIEW хороших материалов | **≤20%** отдельно от BLOCK | Все проверенные человеком качественные материалы |

Отдельно считать метрики по конкретному правилу (особенно E02, E04, E05, E18), по material type и по истинным/подложенным ошибкам; считать `REVIEW` пропуском для автономности и **не считать BLOCK успешным обнаружением без верной причины**. Ошибки с высокой тяжестью не компенсируются средним score.

Пример статистической оценки из ревью: для демонстрации вероятности обнаружения ≥95% при **нуле промахов** требуется около 59 независимых положительных случаев на **каждый** класс (односторонняя 95%-ная граница: `0.05^(1/59) ≈ 95.05%`). Для верхней границы ложных BLOCK ≤5% при нуле ошибок также нужно порядка 59 хороших случаев; при одной ошибке требуется около 95 (точный односторонний интервал зависит от принятой процедуры). **59 не даёт доказательства цели 99%**: ей нужна существенно большая выборка. Для 85% смысловой доли при малом N интервал будет широким; не рекламировать точку как гарантированную точность.

Gold set должен быть **отложенным**, с отдельными synthetic и real-world срезами, стратификацией по типам и классам, неизменяемыми ожидаемыми метками и разметкой причин. Реальные обязательные проверки: 12 случаев C3-08 и ошибки из проб C5-01 (выдуманный URL, `$1.7B` вместо `A$1.7B`, перестановка дат, чужой факт, завышение вывода); C4-02 (цитата не из источника, завышение вывода). Сведения о них взяты только из комментария Claude, не из локальных файлов. Существующие 24 размеченных утверждения `capacity-factscore-ab` покрывают тему мощностей и годятся лишь как **дополнительный** узкий срез, а не gold set целиком; по разрешению владельца их можно предоставить отдельно. 68 синтезов ленты недостаточно для широких уверенных заявлений, 12 из них упомянуты как дефектные.

**Открытое решение владельца:** принять/скорректировать четыре порога, объём ручной разметки good set и минимальную confidence/отложенную выборку. Без него C3-09 остаётся на ревью; переход к C3-10 не начинать.

### Матрица приёмки дополнений (документ, не код)

1. Любая правка payload/evidence, включая карту, делает прежний PASS непригодным; нет атомарного compare-and-swap — нет публикации.
2. REVIEW для каждого типа имеет исполнителя, лимит правок и TTL; частичный выпуск допускается только после новой проверки.
3. EvidenceBundle имеет источник происхождения, статус извлечения и приватные ссылки; отсутствие текста не подменяется генерацией.
4. 30 материалов не порождают безграничных вызовов; при 429/503, отсутствии независимой модели или квоты система не выпускает непроверенное и показывает тревогу.
5. Сигнал без G2/G5/G6, повышение стадии без источника и дубликат опубликованного события не проходят; заголовок оценивается отдельно.
6. Критерии 99% / 85% (гипотеза) / 5% / 20% предложены с планом отложенного замера, но ещё требуют решения владельца.
