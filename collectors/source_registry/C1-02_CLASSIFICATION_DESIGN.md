# C1-02: классификация лент по десяти классам BOHUN и способу доставки

**Статус:** offline-кандидат для ревью; не интегрирован в Source Manager, Inoreader, Web Monitor или рабочую БД. Владелец должен получить результат на **138 проверенных лентах** и вручную сверить случайную выборку **50**; допуск: минимум **45/50** правильных классов (**≥90%**). Никакой тест на синтетике не заменяет эту приёмку.

## Таксономия владельца

| Поле `source_class` | Класс из `PROJECT_PLAN.md` | Пример доказанного назначения |
|---|---|---|
| `grants` | гранты | грантовые программы, funding calls |
| `tenders` | тендеры | открытые торги, invitations to bid, RFP |
| `procurement` | закупки | awards, заказы, заключённые контракты |
| `company_news` | новости компаний | корпоративные пресс-релизы |
| `media` | медиа | самостоятельные новостные издания |
| `investments` | инвестиции | фонды, раунды финансирования, сделки |
| `startups` | стартапы | инкубаторы, акселераторы и стартап-ленты |
| `technology` | технологии | патенты, технические публикации, научные исследования |
| `laws` | законы | нормативные акты, официальные бюллетени |
| `other` | другое | не хватает оснований или источник вне классов |

Класс относится к **основной функции потока**, а не к одному заголовку или владельцу сайта. Отличать: грант ≠ государственная закупка; приглашение участвовать в торгах ≠ присуждение контракта; медиа, перепечатавшее пресс-релиз компании, остаётся медиа. Если источник мультиформатный, требуется выбор человеком, а не повышение вероятности «по названию сайта». Автоматические правила из `classification.py` намеренно узкие; при неясности результат `other/needs_review`.

## Способ доставки: отдельное независимое поле

`delivery_method` может быть `rss_atom`, `api`, `web_monitor`, `email`, `manual`, `unknown`. Метод **не** выводится из класса, имени, домена, ссылки на главную или текстового ответа LLM. Только переданный документированный `delivery_evidence` с `method`, `status=confirmed`, `ref` (идентификатор успешной технической пробы) даёт `delivery_status=evidenced`. Два подтверждённых разных механизма → `conflict`, нужен выбор маршрута; запись `failed/unknown` не даёт подтверждения. Это *проверка формы переданного свидетельства*, а не криптографическая или сетевая проверка его подлинности. Подлинность ref и результаты тестового fetch должны подтвердить подключающий модуль.

Пока нет подтверждения технической доставки, результат имеет `unknown`, даже для подтверждённой медиа-ленты. Никакая классификация не вызывает quickadd, HTTP, DNS, модель, SQL или публикующий маршрут.

## Путь классификации и контракт модели

1. `classify_batch(sources, propose=None)`: максимум 500 источников, не более 20 заголовков на источник, максимум 500 символов текста описания/заголовка. У каждого уникальный `source_id`, HTTPS URL, `title`, необязательный `description`, `sample_titles`, `delivery_evidence`.
2. `_rules`: узкое правило с текстовым свидетельством **только в описании**, если лидер однозначен. При равенстве категорий не выбирает случайно.
3. При отсутствии однозначного правила опционально вызывается `propose(prompt_packet(source))`, **внедряемая функция без модели и ключей**. Системная инструкция хранится как `PROMPT` в том же файле; пакет ограничен полями `source_id/title/description/sample_titles`, не содержит токенов и полного текста статей.
4. Модель должна вернуть ровно `source_id,source_class,evidence_quote`. Код принимает только десять классов и **дословный фрагмент** из описания/заголовка. Некорректные JSON-поля, несоответствие ID и выдуманная цитата → `needs_review`. Даже правильное предложение имеет статус `proposed`, не owner_approved.
5. `assess_sample(predicted, labels)` принимает **ровно 50 вручную подтверждённых меток** по source_id. Выдаёт `correct/50`, долю и `meets_90pct`; `needs_review` учитывается отдельным показателем автономности, а корректность owner-класса (включая `other`) оценивается независимо. Gold set нельзя делать из предсказаний модели.

Не запускайте `--apply` и не добавляйте новые подписки как побочный эффект этой карточки. Перед C1-03 нужен отдельный проверенный identity-контракт для feed URL, источника, метода доставки и повторной обработки.

## Чтение реальной выгрузки и вычисление приёмки (offline CLI)

Добавлен `collectors/source_registry/classification_cli.py`, не требующий сторонних зависимостей. Принимает только локальные JSON-файлы размером до 1 MiB, отвергает дубли JSON-ключей и NaN, не выполняет HTTP/DB/модельные запросы и не пишет файлы. Выводит JSON в stdout; ошибок с содержимым статей и путями на stderr не печатает.

Пример `/private/feeds.json` (вымышленная запись, **не** реальный проверенный feed):

```json
{"sources":[{"source_id":"feed-001","title":"Official tender portal",
 "url":"https://tenders.example.org/feed","description":"Tender notices and invitations to bid",
 "sample_titles":["Invitation to bid for maintenance"],
 "delivery_evidence":[{"method":"rss","status":"confirmed","ref":"synthetic-probe-001"}]}]}
```

Пример формата `/private/human-labels.json` (выборка в настоящем запуске должна содержать ровно 50 **независимо размеченных** идентификаторов):

```json
{"labels":{"feed-001":"tenders"}}
```

Команды **после получения подлинной выгрузки**:

```sh
python -B -m collectors.source_registry.classification_cli --input /private/feeds.json --require-138 > /private/c102-report.json
python -B -m collectors.source_registry.classification_cli --input /private/feeds.json --gold /private/human-labels-50.json --require-138 > /private/c102-evaluation.json
```

`--require-138` отказывает, если источников не ровно 138 или у хотя бы одного нет переданного `confirmed` технического свидетельства доставки; **это проверка структуры входного доказательства, не реальная сетевая валидация**. Ответ `owner_approved=false` всегда, реальные `live_probes` не выполнялись. Порог 90% считается только из **собственного** `--gold`, а не из предложений модели. Синтетические 138 записей и 50 меток проверяют только работу кода.

**Новые офлайн-тесты:** 9 для CLI, всего 32 метода в двух файлах `test_classification*c102.py`; полный запуск в этой сессии не подтверждён. Состояние карточки: **ожидает реальную выгрузку 138 проверенных лент и независимую ручную оценку 50**. Никаких записей в Inoreader или другие рабочие системы.

## Воспроизводимая выборка 50 для владельца

Чтобы проверка 90% не зависела от отбора только очевидных лент, `classification_cli.py` теперь ранжирует все `source_id` по SHA-256 от `seed + ":" + source_id` и отдаёт **ровно 50** идентификаторов в `review_sample_source_ids` при количестве источников ≥50. Порядок входного файла и предсказанные категории на выборку не влияют. `review_sample_seed` записывается в отчёт. Владелец может задать другой публичный `--seed` **до** разметки, зафиксировав его в записи приёмки.

Файл `--gold` должен содержать **именно эти 50 ID** с человеческими метками, иначе `GOLD_SAMPLE_IDS_MISMATCH` и оценки нет. Это защищает от случайного или намеренного выбора более лёгких примеров. При менее чем 50 входных источниках метрика приёмки невозможна. Для выполнения реального критерия по-прежнему нужны первичные данные 138 подтверждённых потоков и независимая человеческая разметка; технические `ref` в JSON пока являются непроверенными утверждениями поставщика данных.

Обновлено: **34 офлайн-тестовых метода** в двух тестовых файлах; результат их фактического выполнения пока не получен.

## Офлайн-предложения модели из файла (дополнение 05.11)

Для полной офлайн-проверки без API к команде добавлен `--proposals /private/c102-proposals.json`. Это **не** запуск модели: файл формируется вне классификатора, например отдельным разрешённым исследовательским процессом. Структура:

```json
{"proposals":[
  {"source_id":"feed-001","source_class":"tenders","evidence_quote":"Tender notices"}
]}
```

Код требует правильную оболочку, не более 500 предложений, известные и неповторяющиеся `source_id` и отсутствие дополнительных полей. Затем существующий `classify()` проверяет значение класса и буквальное присутствие цитаты в описании или заголовках. **Предложение остаётся `proposed`**, не `verified/owner_approved`, не утверждает доставку, и не применяется там, где уже найден однозначный явный класс. Отсутствие предложения либо неверный ответ переводит источник в `needs_review`. Итоговый отчёт добавляет только числа `external_proposals_supplied` и `external_proposals_accepted`, чтобы видеть их вклад.

Пример команды:

```sh
python -B -m collectors.source_registry.classification_cli \
  --input /private/feeds.json \
  --proposals /private/c102-proposals.json \
  --require-138 > /private/c102-with-proposals.json
```

**Тестовая матрица:** дополнительно семь офлайн-тестов для успешного предложения, выдуманной цитаты, неизвестного/повторного source_id, посторонних полей, некорректного исходного объекта и чтения из локального файла. Всего теперь **41 тестовый метод** в двух файлах. Полный Python unittest репозитория всё ещё **не запускался** в текущей среде (GitHub DNS недоступен); PASS не заявляется.
